While the FortiGates are still building up the cluster, you can already see something new in the CLI. 
Open the CLI of the FortiGates
	
![System - HA](/files/695307449dd5a0e2c9a49b4c90ebb42c/FortiGate1_CLI_Primary.jpg)

As you can see, you will now also see the role of the device in CLI. This is a small change but it does make it easier to identify on which firewall you're making the configuration.
	
Now let's head back to the GUI to see if the cluster has been created. Let's discover what is new. Go to `System > HA`

Here you will see all the firewalls inside your cluster, their status, sessions and a lot of other information. Now select the secondary firewall.
	
![System - HA](/files/4460d4c2c7286c3004a8a27605a0a375/Select_secondary.jpg)
	
Click `Diagnostics and Tools`
* At the top you will see information about the device
* There is a `Force resync` when the cluster is not synchronized. It will be greyed out when the clust is in synch.
* Under `Actions` you can now Force HA failover

![System - HA](/files/40697aeb3a74f8a0409fc8ae000f23d8/Extra_Info_HA.jpg)

Under `config diff`, you will see what the differences of the firewalls within the cluster.

![System - HA](/files/8302cda76b8f82b48e6d154a17c7cca6/Config_Sync_Not_In_Sync.jpg)
	
If you're HA cluster is still not syncronized, you can force resync on the secondary firewall.
	
If that still fails, login to the CLI of both devices and use both CLI commands on each FortiGate
	
```
fnsysctl killall hasync
```
	
```
fnsysctl killall hatalk
```
	
After that you will see that the FortiGates are in sync.
![System - HA](/files/33195b13cd61112079d75cdcab4d7057/HA_In_Synch.jpg)

Next up, let's trigger a failover via the GUI. Many different reasons you want to do this:
* Planned hardware maintenance
* Testing failover readiness
* isoltating performance issues
* resolving state anomolies

Make sure you are in `system > HA`
Click on the first firewall and go to `diagnostics and tools`
![Diagnostics and Tools](/files/cd2d29be1ec68a62537a83f6af09d11b/Diagnostics_And_Tools.jpg)

Do the failover

![System - HA](/files/211f55379383faeadf0de74a6bf3f510/Force_Failover.jpg)

Accept the warning that you will do the failover

![Failover Warning](/files/7c8cd7993796faad8d97a0f683c5955a/Accept_Warning_HA_Failover.jpg)

Once you have accepted the warning, you will see that the failover is in progress.
![Failover in progress](/files/65b76877215ee6a7797aa9e26f11a8aa/Failover_In_Process.jpg)

Failover with FortiGates is fast so now you can already refresh your page since you will access a different firewall. After the refresh, you can also login to the firewall.

![Failover in progress](/files/b8f6a56cd3ed21ff31107ab1622b9d61/Refresh_Chrome.jpg)

You will now see that you are inside FortiGate 2.

![Failover in progress](/files/64e78ffc89623bc99c3fc82d88d68e43/FortiGate2_Primary.jpg)

Now let's head back to `System > HA`. According to the Fortinet documentation you should be able to see **Undo HA Failover**, however if you don't see the option you can also force another failover.

You can also do this again to make sure FortiGate 1 is primary again.

After you did the failover you will have to refresh your page and you will see the hostname is FortiGate 1 again.

![FG1 primary again](/files/367064b7977e14601fd7706b0ea2fa41/FG1_Primary.jpg)

<div class="defender-label">New in FortiOS 8.0</div>

Other new changes regarding HA in 8.0.
	
* FGSP synchronizes firewall-authenticated users between FGSP peers. If authenticated users sessions change to a different FGSP peer they do not have to re-authenticate. No special FGSP configuration is required to support this synchronization.
* Software switch member interfaces can be used as HA monitor interfaces
* A specific source IP or interface can be selected for FGSP heartbeat/sync traffic over L3, preventing packet loss caused by ECMP path divergence.
* You can now define failover behavior based on group status instead of individual interfaces. First add multiple interfaces in a group and use these as a monitored group.
